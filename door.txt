Stuck on a fast door
====================

Confirmed 2026-09-14 from a pusher-stop report. Not a theory any more.

What happens
------------

    S: pusher-stop seq=281 lost=313 org=1904.3 1388.03 47.0157
       vel=179.033 -471.55 103.6 -> 179.033 0 93.2001
     pusher=door at=82.5704 0 0 vel=400 0 0 shown=115.77 0 0 adv=83ms
        281 MISS d=2.09/471.0 og=0 cl=- sv=-

The server clipped the player's y velocity from -471.55 to zero. The client did
not, and ran on. So the client's copy of that door was *less* obstructive than
the server's: it was shown more open than it was, the player went through a gap
that did not exist yet, and the server stopped them.

Why
---

PP_PlayerPostThink (ssqc/server-antilag.qc) sets

    pusher_advance = (min(ping, pusher_max) - pusher_buffer) / 1000

and the engine reports pushers to that client advanced along their velocity by
it, so the door they are shown is where it will be by the time their commands
land. At ~110 ms ping that is 83 ms of lookahead.

The advance is symmetric, and that is the bug. It is applied whichever way the
door is going:

  - A *closing* door shown early appears more closed. Harmless: the client
    stops short, the server lets them through, prediction under-runs.
  - An *opening* door shown early appears more open. The client walks into a
    gap the server has not opened yet and the server blocks them.

antilag.md already says this -- "late-biased on purpose: showing a door less
open than reality is harmless, more open feels like a wall" -- but the buffer
is a flat subtraction from ping, so it shortens the lookahead without ever
making it directional.

Speed is what makes it bite. 83 ms of a 400 u/s door is 33 units, most of a
body width. The same lookahead on a 100 u/s door is 8 units and nobody notices.
Both of the earlier reports that looked like ordinary walls were also fast
doors, and both of those were predicted correctly -- so this is not every fast
door, it is a fast door caught at the wrong moment.

The fix
-------

Advance a pusher only where doing so makes it *more* obstructive to that
player, never less. In practice: advance a door that is closing, leave an
opening one where it actually is. Under-prediction costs the no-prediction
baseline; over-prediction costs a wall that is not there.

The mod knows the direction -- a door carries its state -- and the engine does
the advancing, so it needs a per-pusher gate: a field the mod sets on pushers
that are safe to advance, which SV_Snapshot_AdvancePusher honours. Server-side
engine change plus a mod change, both in scope.

Cheaper interim if that is too much: clamp pusher_advance by the pusher's own
speed, so fast doors get little or no lookahead. Blunter -- it gives up the
correction on exactly the doors where it is worth most -- but it is one line
and it is in the safe direction.

Instrumentation
---------------

PP_ReportPusherStop, same file, fires on a loss of >200 u/s within 64 units of
a pusher's *bounding box* (>600 u/s when no pusher is near). Prints where the
pusher was, where that client was shown it, and the advance used. Two earlier
misses read as ordinary geometry because the first version used findradius,
which measures to a brush model's centre -- a door wide enough to stand at the
edge of is further away than its own size.
